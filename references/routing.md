# 调度协议

## 三档启动

三档是模型读懂委托后、调用工具前的制作选择，不是任务JSON的mode，也不是按秒数、镜头数或“高燃”一词分档。先看交付范围，再看是否明确要求重构已有戏。明确只要剧本、讨论、单格修图或已有工程局改时，保持相应任务，不强制双轨或新建立项。

| 触发 | 实际执行 | 交付前核对 |
|---|---|---|
| **极速直出 Fast-Cut**：单段或可独立出稿的定稿片段，目标与首尾明确；新创作的简单场面也适用。 | 取必要人物、起止状态、锁定原句和时长，直接排切点，按需读摄影、表演、动作、特效、声音等方法，不建task.json、不跑plan/init。不把“已有打斗”当作授权重排剧情。 | 看时码、原句、关键动作和末态。仍按完整模板出主稿和可独立复制的直投稿；只要其中一版就只展示该版。快的是准备，不是删栏目。 |
| **高燃重构 Action/VFX Overhaul**：已有戏，明确要求重新编排交锋、招式、视效或节奏，而非只描述一场新戏。 | 改前从原稿摘出“谁因何行动→关键转折→胜负、代价与持物→段尾钩子及下集起始条件”。钩子包括观众此刻**还不知道什么**。用动作、特效、摄影、声音方法重排可动的攻防节拍、观看顺序和爆发点。不默认砍原台词、倒置因果、加能力或换结局。 | 把原稿与两版成稿逐项对照锁定点。没给下集钩子就保留原段末态，不编下集；方案确需动锁定项时只说明冲突，取得具体授权前用不改剧情的拍法。 |
| **完整工程 Full Production**：跨集长篇、多段需要统一资产与连续状态并反复交接，或明确要求可保存/续跑的工程。 | 按下文建工程：核对完整来源和逐事件需求，按段规划、分工、编译、复核与装订；全集资产一次，各段独立直投。九宫只在需要空间验证或明确要求时启用。 | 跨段核对人物、资产、声画末态与钩子；用实际运行回执区分已做和未做。 |

混合请求按范围嵌套：长篇中只请重构一场，不重启整集，调用重构方法并核对相邻段；若交付的是整季工程，其中指定的打戏按重构锁点处理。短镜含大特效可以多读一个专业库，不因此升级为完整工程。三档共享同一画风选择和专业质量标准，不把档名写进直投稿。

遇到写实攻防、复合大招或冲击帧，按[专项表](specialty-selection.md)选择适用的本地专业导法；轻量档手工阅读，工程档登记ID并核对实际装入。不切换独立Skill，也不让来源包覆盖已选交付模板。
遇到复杂续段或跨切口必须保住的决定，先用[导演前置](production-specialties/director-handoff/prepare.md)确定本段可见因果与已证实尾态，再把同一事件交给[分镜与续接](production-specialties/director-handoff/guide.md)及[正文编译](production-specialties/director-handoff/compile-bridge.md)；单段没有这些问题时不另做交接卡。跨风格拍法和细表情独立取用，不默认三个都读。

## 语义识别与程序补调
先按[创作准备](creation-preparation.md)确定忠实改编、授权扩写或仅补拍法。只扩写不建立生产workflow；以下是进入工程后的程序化调度，不是直出与重构的前置门槛。
模型先读取完整来源，提取事件、对白、约束和逐事件能力需求。当前用户意图决定mode，不用关键词推断维护授权。用户不必列模块；features是提示，程序会结合底稿结构和需求清单补调。

任务JSON例：`{"mode":"prompt","features":[],"scope":[],"reason":"含对白和动作；请由底稿核对专业需求"}`。
mode：prompt主稿、revise单事件局改、grid已有主稿九宫、edit_grid单格修改、workbench保存恢复、discuss技能讨论、maintain明确授权的维护。
features：action/performance/vfx/assets/sound。程序从登记对白补表演和声音，从事件需求或保守声响信号补声音；从events.requires和requirements补能力；少量攻防/法术词只作保守补调信号，不代表自然语言理解，也不能以无命中判定无需模块。模型必须逐事件检查特殊需求。
专项按[专项登记](specialty-selection.md)写入对应需求的specialties；不依赖特定中文词也能明确装入白名单资料。专业决策与协作交接遵循[专业职责](design-boundaries.md)。

## 路线
prompt/revise：source → 按底稿与需求覆盖补齐assets/action/performance/vfx/sound → camera → compile → validate。
grid/edit_grid：source → 必要assets → sampling → validate。已有主稿的动作由主稿核对，不强制重新设计；无主稿先走prompt。
workbench：workbench → validate。discuss只讨论；maintain读取维护制度并登记明确授权，不由程序自行改代码。

## 执行中补调
当前模块发现遗漏需求，用discover提交需求ID、kind、description、source_ids、event_ids、source_quote及原因。引用必须存在于源文，不能借补调新增剧情或能力。多项同时发现就批量登记。
需要专项时在新需求附specialties数组；同样受真实引句、负责事件与专业一致性检查。改剧情回创作准备并保存旧底稿重新init，不借补调越过授权。
程序重建计划，保留共同且有效的上游结果；新增/受影响的工序起及其下游失效并存档。不能拿旧摄影/编译结果绕过刚补入的动作或声音工序。补调与返修共享最多两轮预算，耗尽则明确未解决内容，不能静默删需求。

## 读取与提交
context返回实际规则文件、专业分配的事件、必要前后状态、需求覆盖表及上游结果。已声明具体事件覆盖时，专业模块只提交这些事件，并附版本回执。submit必须携带当前context文件；上游、需求、规则或返修轮次变化后重新取context。回执只能证明与当前提供的规则包一致，不能证明模型真正理解或执行了文字。

绑定项目时，以本次范围内的事件、需求清单和显式features决定专业包。简单无对白、无专项效果的镜头只读当前工序的通用规则，不预载对白、表演、表演摄影、声音或招式特效的方法；编译仍读完整模板，复核仍对照正文。短不等于简单：一秒内若有关键反应、明确音效或特效展开，就登记相应需求，按工序加载原有专业方法、专项和库条目。例如单拍廊灯轻晃不读招式库；灯影离墙并沿地滑走，若这是要表现的异象，就登记特效需求，补调成形与传播。不要拿计划的候选路径清单当成阅读任务，以实际context.rules为准。

续用旧运行先check。若标记按旧规则检查，历史通过仍保留为旧版结果，不视为当前通过。用refresh-rules另存；从第一处实际下发规则变化的工序起复跑，因此依赖它的下游也要更新，前面未受影响的交接不重做。规则没变则无需重跑。命令和旧合同迁移另见[工具接口](tool-interface.md)。

需求引用通过不等于语义落实。全稿任务的 source 核对全部来源的每个非空段落，局部任务核对关联来源，compile与validate分别给出每项需求的实际正文位置，最终仍对照原文检查。详见coverage-contract.md。
